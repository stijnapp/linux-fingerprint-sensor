# Adapting synaTudor to HP Spectre x360 (06cb:00ff, driver v11.1)

How the relink works and what the v11.0 → v11.1 jump requires. Read
`captures/FINDINGS.md` first for why we're doing this (clean libfprint driver is a
dead end for this secure family).

## The relink mechanism (synaTudor)

synaTudor does **not** reimplement the protocol. `libtudor` is a userspace **PE
loader** that loads the real Windows driver DLL into memory and provides Linux
implementations of every Windows / WDF / CAPI / BCrypt API the driver imports. The
driver's USB calls are routed to **libusb**; its crypto to **OpenSSL**. A small CLI
(`tudor_cli`) drives enroll/verify/identify against it.

- The driver blob is embedded at build time via `ld -r -b binary`, producing symbols
  `_binary_libtudor_synaWudfBioUsb104_dll_start/_end`. `libtudor/src/tudor/driver.c`
  references those exact names, so our v11.1 DLLs are staged **as the `104` filenames**
  (`scripts/setup.sh` does this). The PE loader resolves the driver's WBF entry points
  (`FxDriverEntryUm`, `WbioQuerySensorInterface`, …) by **export name**, so the file
  version in the name is irrelevant — only the imports the DLL needs matter.
- The CLI selects the device by VID/PID from the command line: `-P00ff` (default is
  the Lenovo `00be`). No source change is needed to target our sensor for the CLI path.

## Lineage of the three drivers

| Gen | DLLs | Sensor | Who |
|---|---|---|---|
| "104" | synaWudfBioUsb104 / synaFpAdapter104 | 06cb:00be | synaTudor base (Lenovo SoftPaq) |
| "110" | …110 | 06cb:00f0 | elitebook840 port (`synaTudor-hp110.patch`) |
| **"111" / v11.1** | **…111** | **06cb:00ff** | **us (HP Spectre x360)** |

The `synaTudor-hp110.patch` adds the Windows APIs the **newer HP driver generation**
calls that the 104-era shim lacked: `GetSystemFirmwareTable` (SMBIOS host identity for
pairing), `CallNtPowerInformation`, a real `GetModuleHandle(NULL)`, a minimal USER32
window layer (`CPowerStateWindow`), `WTSRegister/UnRegisterSessionNotification`, CAPI
symmetric AES (`CryptSetKeyParam`/`GetKeyParam`/`Encrypt`/`Decrypt` — the newer driver
uses legacy CAPI where 104 used BCrypt), and `LoadLibraryW`. These are
**version-agnostic to the HP generation**, so we reuse the patch wholesale; only the
DLL-staging step differs (111 instead of 110). The patch applies cleanly to the pinned
base `31dfdb0`.

## v11.1 import coverage (static analysis)

Imports were dumped from both v11.1 DLLs (`objdump -p`) and diffed against the symbols
libtudor implements after the hp110 patch. **213 distinct imported functions; 75 are
not provided even after the patch.** The PE loader does not fail on an unresolved
import unless it is *actually called* — it points each at a stub that aborts on call
(with `-DDBGIMPORT=true`, logging `Unresolved import <name>@<lib> called!`). So the 75
are an upper bound; the real work is the subset hit during open/pair/enroll.

**A) Noise (38) — listed by the statically-linked MSVC CRT, not on the pairing path.**
Console I/O, SEH unwinding (`Rtl*Unwind`, `__C_specific_handler`), `EncodePointer`,
locale, WPP tracing (`GetTrace*`), stdio file-positioning. Don't pre-stub these; only
act if one actually aborts.

**B) Watch-list (37) — plausibly invoked; add a stub when DBGIMPORT shows it.** Each is
small. Likely-needed first, with the cheap implementation:

| Import(s) | Purpose | Stub |
|---|---|---|
| `CryptAcquireContextW` | CAPI init (W variant; base has the A variant) | wrap existing `CryptAcquireContextA` |
| `InitializeCriticalSectionAndSpinCount` | sync init | init a critical section, ignore spin count |
| `LoadLibraryA` | helper DLL load (patch added `LoadLibraryW`) | wrap `LoadLibraryExW` after A→W |
| `CoTaskMemAlloc` / `CoTaskMemFree` | COM allocator | `malloc` / `free` |
| `CreateMutexA` / `OpenEventW` / `ReleaseMutex` | sync objects | back with existing sync shims |
| `CreateFileW/A`, `CreateDirectoryW/A`, `DeleteFileW`, `MoveFileExW`, `FindFirst/Next/Close` | config/calibration persistence | map to POSIX file I/O under the store dir |
| `RegDeleteValueA` | registry (base has a reg shim) | extend the reg shim |
| `PowerSettingRegister/UnregisterNotification` | power notifications (beyond the v11.0 `CallNtPowerInformation`) | return success / a dummy handle |
| `GetNamedPipeClientComputerNameW` / `GetNamedPipeClientProcessId` | pipe-peer identity (adapter IPC) | return fixed local identity |
| `CM_*` (6, cfgmgr32) | device-interface enumeration | likely bypassed (libusb hands the device in); stub to "no devices"/success if hit |
| `AllocateAndInitializeSid`, `FreeSid`, `InitializeSecurityDescriptor`, `SetSecurityDescriptorDacl`, `SetEntriesInAclA` | build security descriptors for pipe/files | benign success, opaque non-NULL handles |
| `CancelIo` | I/O cancel on teardown | return TRUE |

> The complete absent list is reproducible: `comm -23 <(objdump-imports) <(WINAPI-shims)`.
> Re-run after any rebuild to re-check coverage.

## The wall — and how we cleared it (RESOLVED)

elitebook reached ~90%: the driver pairs, brings up TLS, AES-GCM auth, and reads the
secure **DB2**, then loops forever inside the closed blob on a stale user record
(`NumCurrentUsers=1`, `_GetCommonPropUsrObjId failed(118)`), so `tudor_open` never
returns. That record lives in the sensor's **persistent flash**.

**Our edge held:** the Windows Hello enrollments were removed via Windows Settings *before*
migrating (a BIOS fingerprint reset does the same safely), so the sensor came up with a
clean DB2 and `tudor_open` returned. From there the remaining blockers were ours to solve:

- **Sandbox `EAGAIN` on thread creation** — glibc's 64 MB per-thread arenas blew the
  sandbox `RLIMIT_DATA`; raised `SANDBOX_DATA_LIMIT` to 1 GB (`tudor-host/src/sandbox.h`).
- **Enroll OK, identify never matched** — the closed matcher only loads templates that are
  **DB2 children of the common-property user**; host-side storage made top-level orphans
  that were never loaded. Fix: route enrollment through the closed adapter's **native WBF
  storage interface** (`SYNA_NATIVE_STORAGE=1`, now default) so `CommitEnrollment` links the
  template as a child → it loads into the live matcher → identify matches. The decoded
  open-time DB2 opcode stream that proved this is in `work/re-notes/template-load-chain.md`.
- **`VerifyFeatureSet` is a no-op here** — we verify by running **identify** and comparing
  the returned template GUID to the enrolled one.
- **dbus-broker drops the launcher when it returns a unix fd** — the launcher serves the
  host IPC fd off-bus over its own AF_UNIX socket via `SCM_RIGHTS`; a 3-rule SELinux module
  (`scripts/tudor_fdpass.te`) lets confined `fprintd_t` use it (SELinux stays enforcing).

End state: **enroll, verify, GDM graphical login, and `sudo` all authenticate by
fingerprint**, password fallback intact. All fixes live in `patches/v11.1-00ff.patch`.

## Build & run

```sh
# 1. deps (Fedora)
sudo dnf install -y meson ninja-build gcc pkgconf-pkg-config openssl-devel libusb1-devel
# 2. build (offline; no root/sensor needed). Embeds hp-driver/ v11.1 DLLs, DBGIMPORT on.
./scripts/setup.sh
# 3a. REAL LOGIN PATH — deploy as an fprintd backend (udev rule, SELinux, PAM, all of it):
sudo ./scripts/install.sh
fprintd-enroll && fprintd-verify          # then GDM / lock screen / sudo all work
# 3b. or the standalone CLI path (poke the sensor directly, no fprintd):
sudo bash scripts/syna-cli.sh             # menu e/v/i/q/w/s; log at /tmp/syna-cli-latest.log
```

Debug loop for a watch-list import: if a run aborts with
`Unresolved import <Name>@<lib> called!`, add a `__winfnc` + `WINAPI(<Name>)` stub
(see the table) in the matching `libtudor/src/winapi/*.c`, `ninja -C work/synaTudor/build`,
rerun. A SIGABRT drops a coredump — `coredumpctl info` shows the call site. After any source
change, regenerate the patch: `git -C work/synaTudor diff HEAD > patches/v11.1-00ff.patch`.
